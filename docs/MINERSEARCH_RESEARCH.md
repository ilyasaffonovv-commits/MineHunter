# MinerSearch v1.4.9.4 — что это на самом деле и как ведёт себя

Всё ниже проверено на этой машине (Windows 11 25H2 x64, права администратора). Где написано «код» — это чтение
исходников GitHub `BlendLog/MinerSearch` тег `v1.4.9.4` (коммит `26f53c7`), где «опыт» — фактический запуск и наблюдение.
Сырые материалы (снимки системы до/после, ETW-трассы, логи, diff-ы) лежат в `research/`.

## 2. Архитектура (код)

`Scanner → Analyzer → ThreatDecision → CleanManager/Handler`. Порядок в `Program.ExecuteScanWorkflow`:
1. `RootkitScanner` (только r77, только собственный процесс — см. §5) → 2. процессы → анализ → **фаза SuspendOnly** (замораживает процесс, закрывает файлу запуск ACL)
→ 3. «всё остальное» (файлы, автозагрузка, реестр, службы, задачи, firewall, WMI, hosts, профили) → **фаза DisableExecuteOnly**
→ 4. сигнатурный скан `*.exe` в 5 корнях → 5. «известные» угрозы применяются сразу, «неизвестные» идут в окно Review (или автоматически, если в реестре `autoacceptunknown=1`) → 6. **Finalize**: kill процессов, карантин/удаление файлов, реестр, службы…
Проверки/повторного скана **после** лечения нет.

Детект держится на зашитых списках IOC (~1000 записей: пути, имена файлов, аргументы, ветки реестра, зашифрованные AES строки `Bfs.Create`) для конкретных семейств
(`ReaItekHD`, `WindowsTask`, `taskhost.exe` в ProgramData, `RDPWinst.exe`, TektonIT/RMS, `DisallowRun`, задачи в `\Microsoft\Windows\WindowsBackup\`…) плюс узкие общие эвристики.

## 3. Что MinerSearch делал с моей системой (опыт)

* Запуск `-so -cm`: **0 угроз** на реальной системе (совпало с независимой проверкой следов старого заражения).
* Изменения в системе при scan-only: только `HKLM\SOFTWARE\M1nerSearch\runcount` (+1 на запуск) и лог в `C:\_MinerSearchLogs`. Файлов/задач/служб/реестра больше не менял.
* Сеть (ETW Kernel-Network, payload-PID): **одно** соединение `193.23.197.229:443` в t+1 с, 0,6 с, ~1 КБ вверх/~5,6 КБ вниз — проверка обновлений. Отправка лога на сервер возможна только из GUI-окна результатов (`FinishEx.SendLogAndHandleErrors`) при `allowstatistics=1`; в консольном режиме этого пути нет.
* Процесс: приоритет **RealTime**, пик ~1 ГБ RAM, ~131–160 с CPU, **31,6 ГБ прочитано с диска** за один проход (2,5–3,5 мин), дочерних процессов нет.
* Привилегии токена: `SeDebugPrivilege` и `SeBackupPrivilege` включены (в scan-only), остальные выключены.
* Крашится при перенаправленном stdout (`Console.BufferWidth`/`GetBufferInfo` → `IOException`), распознаёт «родитель PowerShell» только по имени `powershell` (не `pwsh`), на неверный аргумент вызывает `Console.ReadKey` и падает при перенаправленном вводе.

### Наблюдения по журналам прежних запусков (тестовая машина)
* На машине с настоящим заражением одного семейства (набор «WindowsTask / ReaItekHD / winserv + RDPWinst + RMS + DisallowRun + задачи WindowsBackup + исключения Defender» — это зашитые в MinerSearch IOC) он находил и лечил десятки объектов: сильная сторона IOC-подхода.
* Несколько запусков подряд показывали одни и те же 3 «угрозы» — исключения Defender для `%TEMP%`, `C:\ProgramData`, `*.exe`: что-то возвращало их между запусками (лечится симптом, не причина).
* Пример эвристики с риском ложного срабатывания: в режиме автопринятия неизвестных угроз (`autoacceptunknown=1`) он без вопроса удалил значение IFEO `GlobalFlag` (=512) у exe одной игры — то есть настройку, которую могло поставить само приложение.

## 5. Rootkit-проверка
Проверяет **только семейство r77 (bytecode77)** и **только собственный процесс** (читает заголовки своих модулей, ищет 3 сигнатуры в DOS-заголовке; при находке пытается отсоединиться через `NtCreateThreadEx`).
В режиме `--scan-only` **отключена принудительно** (`no_rootkit_check = true`). Не видит: драйверные/буткит/DKOM/скрытые процессы, любые семейства кроме r77. Подтвердить на живом образце не могу (нужен реальный r77) — вывод по коду.

## 6. Очистка (опыт, режим без `-so`, только на тестовых объектах)
Порядок по журналу: обнаружение → **заморозка** 3 процессов (≈ через 30 с после старта) → сканы → «Threats processing»: **kill** процессов → **карантин/удаление файлов** → **удаление службы**. Верификации/rescan нет.

Что получилось на 6 помеченных объектах:
* обработаны: 3 процесса (kill), 2 файла (карантин), 1 служба (**удалена безвозвратно**, без карантина);
* **не обработаны**, хотя помечены: файлы `taskhostw.exe`, `MinerLabTest_root.exe`, exe miner-подобного процесса — остались на диске (сводка при этом: «Total cured threats: 5 of 5»).
* Причина (код + опыт): `FileThreatObject.Id` = **хеш содержимого**; `ExecuteScanWorkflow` отбрасывает решения с уже обработанным `Id`, а карантин хранится в `HKLM\SOFTWARE\M1nerSearch\Quarantine\<MD5>` — одинаковые копии (обычное дело при реальном заражении) затираются/пропускаются.
* Карантин: файл режется на блоки по 512 КБ в бинарные значения реестра `FileData_PartN` (+ `OriginalPath`, `QuarantinedAt`); задачи/службы/ветки реестра — отдельные типы. Нет SHA-256, нет проверки целостности при восстановлении, нет карантина для WMI/firewall/hosts/удалённых служб.
* Восстановление (`-q -cm -res= 1 -f`) работает: файл вернулся с тем же SHA-256. Но второй помещённый в карантин файл **невосстановим** — запись перезаписана записью с тем же MD5.

## 7. Сильные / слабые стороны

**Сильное:** реально чистит известную семью (проверено историей на этой машине); аккуратные IOC по конкретным кампаниям; работа из-под WinPE; консольный режим; ACL-разблокировка объектов, защищённых малварью.

**Слабое (проверено):** IOC-зависимость и мало общих эвристик; нет объединения улик; слепые зоны WMI/автозагрузка/ярлыки; `RealTime` приоритет и 31 ГБ чтения; нет реального rescan; карантин с коллизиями и без хеша; авто-удаление по одиночной эвристике (пример: IFEO `GlobalFlag`); служба удаляется без карантина; падает при перенаправлении вывода; отправка логов автору при включённой «статистике».

Источники по актуальным семействам, использованным при проектировании правил MineHunter, перечислены в `docs/THREAT_RESEARCH.md`.
