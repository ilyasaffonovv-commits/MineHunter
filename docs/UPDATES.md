# Обновления MineHunter (как это работает и как выпускать новые версии и правила)

## Что видит пользователь

Пользователь запускает `MineHunter.exe`. Программа **сразу**:

1. показывает в правом верхнем углу «плашку версии»: `✓ Версия 1.0.0 — последняя`, `⬆ Доступна версия 1.1.0 — скачать`, `○ Нет сети — проверка пропущена`;
2. если есть новые **правила детекта** — скачивает их, проверяет (SHA-256 **и** подпись RSA) и подключает сама;
3. запускает быструю проверку (можно отключить в «О программе → Настройки»).

Плашка «Доступна версия…» открывает страницу релиза на GitHub — пользователь скачивает новый zip как обычный файл. Сам `.exe` программа подменять **не умеет** (сознательно: самообновляющийся антивирус — лишняя поверхность атаки; правила же обновляются автоматически, потому что это данные, защищённые подписью).

## Приватность обновлений

Единственный сетевой запрос — обычный HTTPS-`GET` публичного [`version.json`](../version.json) и (если правила новее) файла [`rules/core.json`](../rules/core.json). Никаких идентификаторов, хешей, путей, имён файлов или журналов **не отправляется**. Без сети программа работает полностью. Замер: во время проверки у процесса нет сетевых соединений (`tests/tools/probe_network.ps1`).

## Где что лежит

| Что | Где |
|---|---|
| адрес манифеста, репозиторий, открытый ключ подписи | зашиты в программу (`Update/Updater.cs`: `DefaultManifestUrl`, `DefaultGitHubRepo`, `DefaultPublicKeyXml`); `config.json` и пользовательский конфиг могут их переопределить (для форков) |
| манифест | [`version.json`](../version.json) в корне ветки `main` |
| правила | [`rules/core.json`](../rules/core.json) — читаемый JSON, единственный источник (вшивается в exe при сборке в сжатом и замаскированном виде) |
| закрытый ключ подписи | **не в репозитории**: у владельца (`Documents\MineHunterKeys\update_private.xml`), права — только владелец. Потеряете — не сможете выпускать правила без выпуска новой версии программы с новым ключом |

## Формат `version.json`

```json
{
  "latestVersion": "1.0.0",
  "releaseUrl": "https://github.com/ilyasaffonovv-commits/MineHunter/releases/latest",
  "notes": "Что нового",
  "rules": {
    "version": "2026.09.26.1",
    "url": "https://raw.githubusercontent.com/ilyasaffonovv-commits/MineHunter/main/rules/core.json",
    "sha256": "<SHA-256 байт файла rules/core.json>",
    "signature": "<подпись RSA-SHA256 в Base64>"
  }
}
```

## Как выпустить новые правила (чаще, чем программу)

1. Отредактируйте `rules/core.json` и поднимите `version` (формат `ГГГГ.ММ.ДД.N`, сравнивается как строка). Файл должен быть с LF-переводами строк (подпись считается по точным байтам; `.gitattributes` это гарантирует).
2. Для каждого нового правила добавьте `samples` — строки, которые **должны** и **не должны** срабатывать; автотест `MineHunter-cli.exe selftest` проверяет их, поэтому обновление не сможет тихо начать ругаться на обычные команды.
3. Выполните `powershell -ExecutionPolicy Bypass -File tools\publish_rules.ps1 -PrivateKey <update_private.xml>` — скрипт посчитает SHA-256, подпишет пакет и обновит `version.json`.
4. Закоммитьте `rules/core.json` и `version.json`, `git push`. CI (`build.yml`) проверит, что манифест соответствует правилам. У всех пользователей правила подтянутся при следующем запуске.

### Что умеет пакет правил

| Поле | Что делает |
|---|---|
| `cmdlinePatterns`, `knownIocPaths`, `persistenceNameRules`, `knownIocTaskFolders` | правила с `id`, регулярным выражением, весом, категорией, `text` и `textRu` (русский текст идёт **вместе с правилом**, программу пересобирать не нужно) |
| **новее побеждает** | правило с тем же `id` из пакета с большей `version` заменяет старое (можно исправить вес или регулярное выражение); пакет старше на такое правило не влияет |
| `disabledRules: ["ID", …]` | мгновенно выключает шумное правило у всех пользователей — быстрый способ отозвать ложное срабатывание без выпуска exe |
| `knownGoodHashes: { "<sha256>": "имя программы" }` | заведомо безопасные файлы (`TRUST.KNOWN_GOOD_HASH`, −100): исправление ложного срабатывания данными. Если хеш есть и в `badHashes`, побеждает «плохой» |
| `badHashes: { "<sha256>": "семейство" }` | известное вредоносное ПО (100 баллов). **Только из проверенных источников** — неверный хеш это ложное срабатывание у кого-то; в комплект такие списки не входят |
| `minerStrings`, `minerFileNames`, `trustedPublishers`, `heavyAppNames`, `poolDomainRegex`, … | списки пополняются (ничего не пропадает) |
| `samples: { match: […], noMatch: […] }` | проверочные строки правила для самотестов |

Хеши можно также подкладывать локально файлами `hashes*.txt` рядом с программой (`sha256 имя`, `#` — комментарий).

## Как выпустить новую версию программы

1. Поднимите номер в `src/MineHunter/MineHunter.csproj` (`<Version>`) и `Scanning/ScanEngine.cs` (`AppInfo.Version`). Если изменилась логика детекта — увеличьте `AppInfo.EngineRevision` (сбрасывает кэш «выглядело безобидно»).
2. `powershell -ExecutionPolicy Bypass -File build_release.ps1 -Zip` — собирает `MineHunter.exe`, `MineHunter-cli.exe`, `SHA256SUMS.txt` и `dist/MineHunter-v<версия>.zip`.
3. Пометьте коммит тегом `v<версия>` и отправьте его: workflow `release.yml` соберёт, прогонит самотесты и опубликует релиз с zip и суммой SHA-256.
4. Поставьте `latestVersion` в `version.json` (тем же `publish_rules.ps1 -LatestVersion <версия>`) — у пользователей загорится «Доступна новая версия».

## Подпись правил (защита от подмены)

Правила могут расширять список доверенных издателей и хешей — поддельный пакет мог бы «выпустить» вредоносную программу из-под проверки. Поэтому пакет принимается **только** если совпал SHA-256 из манифеста **и** верна подпись RSA-SHA256 открытым ключом, зашитым в программу. Ключи создаются один раз: `MineHunter-cli.exe --gen-signing-keys <папка>` → `update_private.xml` (секрет) и `update_public.xml` (вставляется в `DefaultPublicKeyXml`).

Программа отклоняет пакет, если: адрес не HTTPS (исключение — loopback для тестов), размер > 8 МБ, SHA-256 не совпал или не указан, подпись неверна или отсутствует, файл не разбирается как правила или в нём нет версии. Всё это проверено автотестами (`selftest`, раздел «Update flow end-to-end» — поднимается локальный сервер и проверяются все ветки, включая подмену), а проверка живого репозитория — командой `MineHunter-cli.exe update-check`.

## Куда ложатся скачанные правила

`%ProgramData%\MineHunter\rules\update-*.json`. Папка данных доступна на запись только администраторам (права выставляются при первом запуске), поэтому обычная программа не может подложить туда своё «правило». Наборы правил объединяются: вшитые в exe + папка `rules\` рядом с программой + скачанные обновления; для одного `id` побеждает пакет с более новой `version`.

## Форки

Замените в `Updater.cs` три константы (`DefaultGitHubRepo`, `DefaultManifestUrl`, `DefaultPublicKeyXml`), создайте свою пару ключей и подписывайте свои пакеты — программа форка будет доверять только вашему ключу.
