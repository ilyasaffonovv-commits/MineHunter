# Обновления

## Что происходит при запуске

1. Главная программа (и обе программы проверки) скачивает `version.json` и показывает состояние: последняя версия, доступно обновление, обновление скачано и проверено, нет сети.
2. Если в манифесте опубликованы более новые правила и включено автоматическое обновление правил, программа скачивает пакет, проверяет его и подключает.
3. Если в манифесте есть более новая версия самой программы и включено «Скачивать новые версии автоматически» (включено по умолчанию), программа скачивает пакет, проверяет его и откладывает **до вашего клика** («Обновить сейчас»). Установка сама по себе без вашего согласия не происходит.

Проверка при запуске не начинается сама: быстрая проверка это «MineHunter Quick Scan.exe» или кнопка в окне.

## Обновление самой программы

Обновление устроено так, чтобы неудача не могла испортить установленную версию.

1. **Объявление подписано.** Раздел `app` в `version.json` содержит версию, адрес zip, SHA-256, размер, самую старую версию, которая может обновиться автоматически (`minVersion`), и подпись RSA-SHA256 (тем же ключом, что и правила) над строкой `MineHunter-app|версия|sha256|размер|minVersion|адрес`. Если подмена затронет хоть одно поле, подпись перестанет сходиться. Без встроенного открытого ключа обновление не принимается.
2. **Пакет проверяется до распаковки.** Скачивание идёт во временный файл; размер и SHA-256 сверяются с подписанными значениями; адрес должен быть HTTPS (loopback разрешён для проверок).
3. **Распаковка безопасная.** Пакет распаковывается в отдельную папку, а не поверх установленной. Пакет с путём, выходящим из этой папки (`..\`), отклоняется целиком. Обязательные файлы: `MineHunter.exe`, `components\MineHunter.Core.dll`, `components\MineHunter.UI.dll`, `components\MineHunter.UpdateHelper.exe`. Если файлы пакета несут подпись Authenticode, она должна быть действительной (наши сборки без сертификата не подписаны, поэтому это дополнительная проверка, а не основная).
4. **Установка отдельным помощником.** `MineHunter.UpdateHelper.exe` копируется во временную папку и запускается оттуда (чтобы можно было заменить и его самого). Помощник не ходит в сеть и ничего не решает про доверие, он: ждёт, пока закроются все программы MineHunter; сохраняет в папку резерва каждый файл, который собирается заменить; копирует новые файлы (`config.json` и `Reports\` не трогает); сверяет SHA-256 каждой копии; при **любой** ошибке возвращает старые файлы и удаляет добавленные; пишет `result.json` и запускает программу снова.
5. **Результат виден.** При следующем запуске главная страница сообщает: «обновлено до X» или «обновление до X не удалось, предыдущая версия возвращена и работает». Предыдущая версия остаётся в резерве, вернуться к ней можно в Настройки > Обновления.

Что проверено (`tests/update_helper_tests.ps1` запускает настоящий помощник на поддельных установках в temp; самотест проверяет принимающую сторону на локальном HTTP-сервере): хорошее обновление; подпись другим ключом; изменённые размер, хеш, адрес; неподписанное объявление; подмена содержимого пакета при том же размере; пакет с `..\`; пакет без главной программы или помощника; слишком старая версия; та же версия (понижение не предлагается); не-https адрес; нет ключа; нет сети; сбой посреди установки (файл занят) с откатом всех файлов; невозможность сделать резервную копию (ничего не меняется); ожидание закрытия программы; отказ, пока программа ещё открыта; команда отката. **Не проверено:** установка настоящего релиза с GitHub на другой машине (первый такой релиз это 1.1.0: версии 1.0.x обновляются до него вручную, у них нет этого механизма).

## Что отправляется

Единственные сетевые запросы это HTTPS GET публичного [`version.json`](../version.json) и, если нужно, файлов [`rules/core.json`](../rules/core.json) и zip релиза на GitHub. Идентификаторы, хеши, пути, имена файлов и журналы не отправляются. Без сети программа работает полностью. Если включить VirusTotal в настройках (по умолчанию выключен), отправляется только SHA-256 проверяемого файла с вашим ключом API, сам файл не загружается никогда. Во время проверки у процесса нет сетевых соединений (`tests/tools/probe_network.ps1` опрашивает их каждые 0,7 с).

## Где что лежит

| Что | Где |
|---|---|
| Адрес манифеста, репозиторий, открытый ключ подписи | Константы в `Update/Updater.cs` (`DefaultManifestUrl`, `DefaultGitHubRepo`, `DefaultPublicKeyXml`). `config.json` и пользовательская конфигурация могут их переопределить. |
| Манифест | `version.json` в корне ветки `main`. |
| Правила | `rules/core.json`, читаемый JSON. При сборке вшивается в exe в сжатом и замаскированном виде. |
| Закрытый ключ подписи | Хранится у владельца репозитория вне репозитория. Без него нельзя выпустить подписанные правила, а при потере придётся выпускать новую версию программы с новым открытым ключом. |
| Скачанные правила | `%ProgramData%\MineHunter\rules\update-*.json`. |

## Формат `version.json`

```json
{
  "latestVersion": "1.1.0",
  "releaseUrl": "https://github.com/ilyasaffonovv-commits/MineHunter/releases/latest",
  "notes": "Что нового",
  "app": {
    "version": "1.1.0",
    "url": "https://github.com/ilyasaffonovv-commits/MineHunter/releases/download/v1.1.0/MineHunter-Portable-x64.zip",
    "sha256": "<SHA-256 zip>",
    "size": 1234567,
    "minVersion": "1.0.0",
    "notes": "Что нового",
    "signature": "<подпись RSA-SHA256 над MineHunter-app|версия|sha256|размер|minVersion|адрес>"
  },
  "rules": {
    "version": "2026.09.26.1",
    "url": "https://raw.githubusercontent.com/ilyasaffonovv-commits/MineHunter/main/rules/core.json",
    "sha256": "<SHA-256 файла rules/core.json>",
    "signature": "<подпись RSA-SHA256 в Base64>"
  }
}
```

## Выпуск правил

1. Изменить `rules/core.json` и поднять `version` (формат `ГГГГ.ММ.ДД.N`, сравнивается как строка). Подпись считается по точным байтам, поэтому файл должен быть с переводами строк LF (это задано в `.gitattributes`).
2. Для каждого нового правила добавить `samples` (строки, которые должны и не должны срабатывать). `MineHunter-cli.exe selftest` проверяет их.
3. Выполнить `powershell -ExecutionPolicy Bypass -File tools\publish_rules.ps1 -PrivateKey <update_private.xml>`. Скрипт считает SHA-256, подписывает пакет и обновляет `version.json`.
4. Закоммитить `rules/core.json` и `version.json` и отправить в `main`. Workflow `build.yml` проверит, что манифест соответствует пакету. У пользователей правила обновятся при следующем запуске.

### Что может содержать пакет

| Поле | Назначение |
|---|---|
| `cmdlinePatterns`, `knownIocPaths`, `persistenceNameRules`, `knownIocTaskFolders` | Правила с `id`, регулярным выражением, весом, категорией, `text` и `textRu`. Русский текст поставляется вместе с правилом. |
| Версия правила | Правило с тем же `id` из пакета с большей `version` заменяет старое. Более старый пакет на такое правило не влияет. |
| `disabledRules` | Список `id` правил, которые выключаются. Так можно быстро отозвать ложное срабатывание без нового exe. |
| `knownGoodHashes` | Хеши заведомо безопасных файлов (`TRUST.KNOWN_GOOD_HASH`, вес -100). Если хеш есть и в `badHashes`, приоритет у `badHashes`. |
| `badHashes` | Хеши известного вредоносного ПО (вес 100). В комплект такие списки не входят; добавлять только хеши из проверяемых источников, неверный хеш даёт ложное срабатывание. |
| `minerStrings`, `minerFileNames`, `trustedPublishers`, `heavyAppNames`, `poolDomainRegex` и другие списки | Пополняются, ничего не удаляется. |
| `samples` | Примеры строк для самотеста. |

Хеши можно также положить локально в файлы `hashes*.txt` рядом с программой (строка `sha256 имя`, `#` начинает комментарий).

## Выпуск новой версии программы

1. Поднять номер в `src/Directory.Build.props` (`<Version>`) и в `AppInfo.Version` (`Scanning/ScanEngine.cs`). Если менялась логика детекта, увеличить `AppInfo.EngineRevision`: это сбрасывает кэш файлов, признанных безобидными.
2. `powershell -ExecutionPolicy Bypass -File build_release.ps1 -Zip` собирает четыре программы, `components\`, `SHA256SUMS.txt` и `dist\MineHunter-Portable-x64.zip` (имя без номера версии, чтобы работала ссылка `releases/latest/download/MineHunter-Portable-x64.zip`).
3. Опубликовать релиз `v<версия>` с этим zip (workflow `release.yml` делает это по тегу).
4. `powershell -ExecutionPolicy Bypass -File tools\publish_update.ps1 -PrivateKey <update_private.xml>` пишет раздел `app` в `version.json`: считает SHA-256 и размер именно собранного zip и подписывает объявление. Затем `publish_rules.ps1`, если менялись правила. Закоммитить `version.json`. После этого у пользователей появится обновление.

Порядок важен: сначала релиз с zip, потом `version.json` (иначе объявление указывало бы на файл, которого ещё нет), и zip в релизе должен быть тем самым файлом, который подписан.

## Проверка пакета

Пакет правил принимается, только если совпал SHA-256 из манифеста и подпись RSA-SHA256 проверена открытым ключом, встроенным в программу. Причина: правила могут расширять списки доверенных издателей и хешей, и поддельный пакет мог бы вывести вредоносную программу из-под проверки.

Пакет отклоняется, если адрес не HTTPS (для проверок разрешён loopback), размер больше 8 МБ, SHA-256 не совпал или не указан, подпись неверна или отсутствует, файл не разбирается как правила или в нём нет версии. Эти случаи покрыты самотестом «update flow», который поднимает локальный HTTP-сервер. Проверка против настоящего репозитория: `MineHunter-cli.exe update-check`.

Ключи создаёт `MineHunter-cli.exe --gen-signing-keys <папка>` (`update_private.xml` и `update_public.xml`). Содержимое `update_public.xml` подставляется в `DefaultPublicKeyXml`.

## Как объединяются правила

Загружаются правила из exe, из папки `rules\` рядом с программой и скачанные обновления. Для одного `id` действует пакет с большей `version`. Папка `%ProgramData%\MineHunter` доступна на запись только администраторам (права выставляются при первом запуске), поэтому обычная программа не может подложить туда своё правило.

## Форки

В `Updater.cs` нужно заменить `DefaultGitHubRepo`, `DefaultManifestUrl` и `DefaultPublicKeyXml`, создать свою пару ключей и подписывать свои пакеты. Такая сборка доверяет только вашему ключу.
